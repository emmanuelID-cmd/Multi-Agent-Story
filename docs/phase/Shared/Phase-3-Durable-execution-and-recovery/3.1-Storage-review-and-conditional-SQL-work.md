## Storage decision

Reuse the existing PostgreSQL rows and JSON fields; no SQL migration is required for the current Phase 3 scope. `runs` already bind a run to its project and Bible and record lifecycle/cancellation state. `tasks` bind each chapter task to its run, chapter index, status, attempt count, and saved input; that input carries the Bible/brief snapshot, Bible version, revision round, and any READ source references already used by the connected workflow. `chapters` and `bibles` have unique run/chapter and project/version constraints. Typed dossier, acceptance, and read-connection records already live in `proposals.data` with owner, version, source, and hash checks at their repository boundaries.

The existing task row can carry the current attempt identity as `(task.id, attempts)` and existing transactions can atomically compare it before saving a result. Phase 3.2 later proved this comparison prevents stale attempts from committing. A migration would have been proposed on `sql-foundation` only if this invariant could not be enforced with existing rows and JSON state. This review itself did not change database rows; I03 and I04 completion evidence is recorded in their respective sub-phase records.
