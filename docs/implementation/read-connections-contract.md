Justin's generation, editing prompts, manuscript format and disabled-by-default workflow remain preserved. READ does not approve a manuscript, produce a Bible or implement Phase 4.

## Runtime configuration and tools

The application entry point is `POST /api/projects/{id}/read`. It calls `requireUser`, `sameOrigin` and the existing five-second/80,000-byte JSON reader. Strict actions are `record_request`, `reader`, `receive_reader`, `consistency` and `resume_revision`; they accept no owner, model, credential, budget or source-text override. The session supplies owner identity. Project and run IDs are checked before source exposure. The opt-in `finishRun` and requested-revision graph paths invoke `executeReadConnectedRun`, which connects actual Reader output to the existing `criticEditorAModel`/`criticEditorBModel` receiving functions. This implementation has not been deployed.

Live dispatch is disabled unless server configuration sets `READ_CONNECTIONS_ENABLED=true`, a key and positive verified input/output pricing. `.env.example` leaves the gate false and rates empty. Construction makes no network request. The existing adapter is `AnthropicReadModel`, model `claude-haiku-5-5`, with its existing medium effort; this phase changes no model selection. Deployment pricing, live availability and calibration are unverified. No live calls were made.

READ operations share a durable allowance for their validated target run, bounded by 60,000 tokens and USD 3, with the existing 120-second per-operation timeout and global three-model-call semaphore. These reservations account for READ usage only; they do not implement a total Writer/Editor/READ run-cost ledger. Each dispatch reserves the remaining allowance under the project lock; confirmed results reconcile usage, while uncertain dispatched failures/timeouts retain the full unsettled reservation and block later spending pending human reconciliation. Reserved amounts are not claimed as confirmed billing. Reader's nested content retry is disabled; the durable coordinator permits one repair without resetting prior usage. Consistency retains one internal retry inside its reserved allowance. Relevant READ history is capped at 200 rows/project; capacity stops rather than deletes history. No automatic trace collector is installed.

## Shared state and version authority

Existing `proposals` JSONB stores version-1 `read_request`, `read_operation` and protected `read_resume` coordination records. This reuses existing SQL columns; no migration is needed or executed. Requests bind authenticated owner/project, exact source run and optional target run, project-state version, approved Bible version, assigned draft revision, editorial round (0–2), task, explicit instructions and source fingerprint. Versions across different artifact types never require numerical equality.

The chapters table has no producer draft-revision column. `draftVersionAuthority=authenticated_assignment` explicitly identifies the draft number as an authenticated writer's snapshot assignment, persisted under lock, rather than a verified producer version. The same run/source identity/draft number cannot later bind different content. Proposal rows also have no producer revision column: the first authenticated request binds their proposal revision label immutably to the real row. Later requests cannot assign that row another revision label. Round uniqueness uses real proposal row identity, ignoring caller-chosen revision labels; changing a proposal/draft number cannot reset it. A different request ID cannot reset the same run/source/round, and a different operation ID cannot reset the request's Reader or Consistency operation. New changed-content assignments require a new revision and appropriate round; a revised proposal needs a new proposal row. These are durable snapshot identities, not evidence that Writer produced draft v5 or proposal v3. Source `origin` remains `unverified` for the database adapter and `synthetic` only in injected fixtures; `verifiedLiveProducer` is always false. Unknown origin does not prevent authorized reading.

Fingerprints cover exact row IDs, ordered chapter text/hashes, Bible identity/version/data/facts, run relationship and assignment identity. Proposal reports additionally bind proposal row/version, full WRITE manuscript digest (including editorial metadata), independent READ source/chapter digest, protected row identity/data digest and base-chapter/Bible digests. Status transitions between `awaiting_read` and `pending` do not change content identity. Changed or unavailable evidence prevents replay and final success. Prior reports remain historical evidence, never authority for changed inputs.

Authenticated run creation saves the exact revision source run and, for round two, separate prior A/B proposal IDs in task JSON. The worker uses these saved pointers rather than selecting a new latest source later. Within the locked READ repository transaction, a cross-run target must be owned, active/not canceled, linked to the same approved Bible, and explicitly bound by those task pointers and editorial intent to the source. The ledger key is the resolved stored target ID. Standalone review may use the same real source/target in completed or active states; failed/canceled sources cannot obtain that exception.

## Coordination and handoff outcomes

Short transactions lock owned project, exact run, Bible (`SHARE`), indexed chapters (`SHARE`) and relevant proposal/operation rows (`UPDATE`) in that order, with stable child ordering and five-second lock/statement timeouts. Dispatch intent and repair usage are saved before model work. No model call or human wait occurs under these locks. Results reacquire and reread sources before retaining success. The row locks also protect against source updates by writers that do not acquire the parent project lock. Live PostgreSQL contention/deadlock behavior is not exercised by synthetic tests.

`receiveReader` runs the actual Editor receiving validator against the retained exact source and recorded request, then separately checks task/round/instruction-presence binding. It persists the selected A/B validator identity, handoff digest/revision, validation acceptance or failed checks/missing evidence/correction. Every receipt has `kind=receiving_validation`; the HTTP caller selects which contract to evaluate. A validation receipt does not prove that an Editor agent took ownership or produced an edit. Feedback reaches Reader as data; it cannot replace editorial instructions or grant tools. A no-handoff timeout/model failure preserves its execution state, produces no receiving receipt and consumes no content repair. Missing Writer rows route to `writer_recovery`; inaccessible storage to `retrieval_recovery`; Reader evidence defects to `reader_correction`; exhausted repair to `human_review`. Repair increments handoff generation, preserves editorial round and retains the initial result.

The actual Editor wrapper separately reserves `accepted_for_execution` only after its receiving validation passes. Duplicate/restarted execution cannot acquire another dispatch. `output_produced` is saved atomically with the validated full Editor result, usage and model identity; another service instance reuses that artifact instead of rerunning the Editor. Failures remain separate. Actual receiving rejection invokes the durable Reader correction path. The opt-in A/B calls are sequential to share one repaired Reader artifact safely; default legacy execution retains its parallel behavior. Worker Editor models remain fixtures, and output provenance is explicitly synthetic/unverified, never verified live Writer/Editor output.

Both generated proposals are preserved as `awaiting_read`, using stable UUID-form identities accepted by the existing human approval route. Each receives its own real READ Consistency operation outside transactions. Final workflow advancement verifies both exact current reports and Editor/source bindings inside the same short locked transaction that makes proposals pending and completes the run. Human approval independently verifies that proposal's exact current report in its acceptance transaction. Partial, stale, mismatched, missing or unavailable reports cannot advance or approve a proposal.

Empty application defaults do not prove that the writer explicitly chose no additional instructions. Production processing requires an authenticated `record_request` bound to the target run. If the worker arrives first it pauses without editorial dispatch; after saving explicit authority, `resume_revision` reserves a request-bound queue intent and requeues only a paused owned run. Concurrent/duplicate resumes cannot enqueue twice. Unknown or unconfirmed queue outcomes remain reserved for human reconciliation rather than being called queued or automatically retried. There is no dedicated UI for this explicit request/resume protocol; use the authenticated API. Preexisting revisions without server-saved source pointers fail closed.

Cancellation and late changed state cannot become successful current results. Partial, failed, canceled, unavailable and exhausted states remain distinct. A crash after reservation leaves a running record with uncertain dispatch outcome; duplicates do not redispatch or acquire another repair. Automatic recovery of an uncertain in-flight provider effect is not implemented and needs human investigation; never clear that record merely to retry. Accepted requests are immutable. Replays recheck owned current sources.

## Prompt and action boundaries

The existing runtime loads separate trusted Reader/Consistency system prompts. Manuscript text, facts, imported JSON and receiving feedback remain data. Reader prepares located observations for all assigned chapters; Consistency checks every chapter and fact. Neither role edits, publishes, accepts proposals or receives SQL/shell/arbitrary-URL tools. Schema and exact-quote/source checks enforce output contracts outside the model. Synthetic injection and Unicode cases establish bounded behavior, not universal prompt-injection detection.
