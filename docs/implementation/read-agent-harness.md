# READ agent harness plan (design, v0.1)

This is a prospective, synthetic-fixture evaluation plan for [the three READ contracts](read-agent-contracts.md), mapped to [PRD v2 draft](../prd/drafts/PRD-v2-draft.md) R01-R29/5g. Expected outcomes below are specified before new implementation. `EXISTING` names narrower current fixture/unit evidence; it is not a pass for the proposed agent behavior. `NOT IMPLEMENTED` and `NOT TESTED` are release gaps. No live provider/model calls or new tests were run for this document.

## Environment and acceptance method

The observed stack is Node/TypeScript, LangGraph.js, Zod, PostgreSQL/Drizzle, a separate worker, and Vitest. The fixture graph in `src/agents/graph.ts` dispatches chapter nodes before `getGenreBenchmarks` in `finishRun`: it violates proposed R03's intake -> accepted two-provider dossier -> planning gate. `src/agents/handoff.ts` builds a five-field fixture but lacks actual source resolution; `src/agents/consistency-shell.ts` returns unavailable. Keep these as gaps, not evidence of full READ operation. The metadata adapter is disabled by default and live terms/provider readiness is unverified.

For each future run, record exact PRD revision/hash, contract/prompt v0.1 or successor, model API ID and effort, tool schemas/allowlist, state schema, harness/fixture versions, and synthetic/live environment. Keep configuration revision distinct from `stateVersion` and dossier/bible/draft/handoff/proposal versions. Use isolated synthetic users/projects, deterministic fixtures, then withheld cases and repeated nondeterministic trials once live operation is authorized. Critical cross-project, approval, stale-write, and forbidden-dispatch assertions require zero failures; 5g targets require all handoffs classified, zero invalid editor dispatches, zero embedded commands gaining authority, zero stale accepted updates, and visible escalation/failure for every exhausted repair. Qualitative craft quality needs independent review; self-scores are insufficient. No threshold or live reliability result is claimed.

## Shared-state and handoff checks

Use assigned ownership for independent READ artifacts and the existing scheduler for dependencies. Future application acceptance should atomically compare expected state version, project/run owner, current task/attempt/owner generation, cancellation, and artifact version, then record the accepted effect. Test simultaneous accepts and verify the *stored* winner and unchanged prior accepted state. A read/check followed by an unconditional write fails this contract. Do not hold locks over model calls or human review. Reassignment needs store-enforced current-owner/fencing evidence; if unavailable, pause instead of accepting two owners. This design does not authorize SQL/schema changes.

Handoff tests separately verify artifact readability, five fields, server-recorded user request, source identity/hash/locator and freshness, coverage, both receiving editor acknowledgments for their assigned tasks, a bounded repair count, and explicit failure/escalation. A metadata summary alone cannot stand in for a full source. Editor behavior belongs to Justin's WRITE lane; integration tests require agreed shared envelopes and fixtures before either lane relies on them.

## Trace and reviewer evidence

Proposed correlated events: `runId`, `traceId`, `agentId`, `parentAgentId`, `taskOwner`, `taskId`, `operationId`, `intentFingerprintRef`, `handoffId`, `toolCallId`, opaque project/resource refs, zoned timestamp and per-stream sequence, PRD/contract/prompt/model/tool/harness revisions, `stateVersion`, expected/actual versions, owner generation, event/status/duration, redacted evidence ref and error code. Distinguish attempted tool call, authorized dispatch, provider response, validated result, accepted state effect, and denied call. Never log credentials, unpublished prose by default, raw injected strings, or private model reasoning. Current READ event interface and retention policy are **NOT IMPLEMENTED**; no terminal viewer proves otherwise.

Future harness viewers subscribe to **one** authorized execution: separate identifiable Research, Reader and Consistency streams plus a correlated workflow view. Opening another viewer must not invoke an agent or provider again. Use Windows Terminal/PowerShell only if supported and authorized; if telemetry or viewer support is absent, record that gap. REVIEWER receives exact fixture inputs, expected/actual assertions, protected state/effect checks, trace references, trial counts, versions, failures and limitations. SECURITY reviews the provider, authorization, stored-data and injection boundaries before any live release. No deployed protection is asserted by this plan.
